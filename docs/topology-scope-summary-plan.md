## Proposed scope (to confirm) — updated with x3cess clarifications
Goal: the summary explains the CONNECTIONS between the nodes in the current scope and says which nodes are in scope. It is not a per-node list. Recenter is a scope change. Summaries are saved and reused; regenerate only when scope or graph changed.

### What "current scope" means
The nodes the user can currently see: the accepted snapshot filtered by the active kind filters (and cycle scope/depth, which already shaped the snapshot). Summary describes **visible nodes**, not discovered-but-omitted ones, and says how many are omitted. Selecting a node does not change the summary. Recenter, depth, cycle or filter change is a scope change and does.

### What it contains (connections first)
1. Scope line: seed, depth, cycle scope, filters, and which nodes are in scope, given as counts per kind plus the few anchor nodes by name (seed, most-connected, top evidence), "+K more". Never a per-node list.
2. Connection narrative, the main body: how the nodes relate, grouped by relationship type and path: direct provenance (source -> article -> claim), actor mentions, inference premises (claims -> inference), Links with their predicate, and Related (tentative). Each group states who connects to whom, the strongest paths from the seed, clusters/hubs, and nodes that are only weakly connected or isolated within the scope.
3. Caveats: omitted nodes/edges, unresolved endpoints, Related is potential context only.

### Scope identity, cache key and invalidation
- **Scope key** (what the user is looking at): hash of seed key + depth + cycle scope + the six filter flags. **Recenter changes the seed, so it is a new scope key.** Filters, depth and cycle likewise.
- **Graph version:** hash of the visible snapshot content that the summary depends on: sorted node keys + revisions and edge ids + kinds/status, combined with `memory_changed_seq` from the same read transaction (the existing authoritative change counter). Order and layout (pan, zoom, selection) are excluded, so they never invalidate.
- **Cache key digest** = hash(scope key, graph version, mode [deterministic or ai], provider, model, prompt version). Reuse is by exact digest: if this scope plus this graph version was summarized before (even earlier in the session, even after recentering away and back) the saved text is shown with no regeneration.
- **Invalidation:** a different digest means the saved row for another version is only shown as "earlier result (stale)" while the new one is produced; nothing is deleted on scope change, so going back reuses the old entry.
- **"Changed recently":** the graph is considered changed when the graph version hash differs from the saved one (primary rule, exact). Optional age bound: do not regenerate more often than once per N minutes (default 10) when only `memory_changed_seq` moved but the visible-content hash is identical (churn elsewhere in the brain), and treat a saved AI summary older than a maximum age (default 7 days) as stale even if hashes match. Scope changes ignore the throttle (always regenerate when no exact entry exists). The failed-run cooldown (120 s) from graph_explanation still applies.

### Where the stored summary lives
New table `topology_scope_summaries` in the main SQLite store (schema migration 43, next to `memory_graph_summaries`): `digest TEXT PRIMARY KEY, scope_key, graph_version, mode, summary, provider, model, prompt_version, node_count, edge_count, created_at, last_used_at`, plus the existing `explanation_record` style diagnostic for failures. The existing `memory_graph_summaries` is keyed by memory_id with a single row, so it cannot hold one summary per scope. Pruned by LRU (keep latest ~50 per seed) and deleted when the seed memory is deleted. Read on snapshot accept (never in draw); written only on completed generation, and only if the digest still matches the current scope when it finishes (late results for an old scope are saved under their own digest but not displayed).

### How it is generated
On snapshot accept or scope change: compute digest -> exact saved entry? show it. Else show deterministic summary immediately, and (if the AI narrative is enabled) schedule generation per the freshness rule above.
- **Default (deterministic, always on, no model):** built purely from the snapshot in a pure function `scope_summary(snapshot, filters) -> ScopeSummary` (core, unit-testable). Cheap, computed on snapshot accept / filter change, never in draw. This is the "no-model fallback" and is what x3cess sees first.
- **Optional AI narrative (explicit action, not automatic):** a "Summarize scope" button writes a short grouped narrative through the **Summarization role** via the existing `graph_explanation` machinery (same job/log/failure card/cooldown), fed a bounded textual brief of the visible scope. Cached with a `SummaryKey` whose graph revision = hash of the visible node/edge keys (+ memory_changed_seq), focus = seed key; scope change => key changes => cached text shown as "earlier result (stale)" until regenerated. States: idle, writing…, ready, stale, failed (failure card, retry), unavailable (no Summarization route -> deterministic text stays). Reasoning for opt-in: topology promises no model work on open, and models cost/latency.
